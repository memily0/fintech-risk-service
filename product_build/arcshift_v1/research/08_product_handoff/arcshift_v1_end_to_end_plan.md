# Полный План ArcShift V1 От Исследований До Сайта На Домене

Дата: 05.11.2026. Цель пользователя: первая полноценная версия продукта,
постоянное получение данных, автоматически обновляемый dashboard и размещение
на собственном домене и сервере. Это план работ; покупка, изменение DNS,
передача данных, обучение и deployment сейчас не выполняются.

## 1 Целевой Результат

Пользователь открывает защищённый сайт, видит поддерживаемые рынки и качество
данных, получает предупреждения, разбирает факторы и историю, фиксирует свою
проверку, формирует отчёт или получает данные через API. Система обновляется
без ручной пересборки CSV, сообщает о сбоях и допускает проверяемое восстановление.

Подтверждены Россия как основа и публичный сервис с регистрацией;
международные факторы служат внешним контекстом. Казахстан отдельно
не включаем. [Спецификация](v1_product_specification/README.md) описывает
конечное предложение функций и приёмки. У релиза должны быть
определённые пользователи, задачи, рынки и горизонты. Это
полноценный ограниченный продукт, а не обещание всех стран, всех типов риска
и любого банковского процесса сразу. Функции и корректность оцениваются вместе.

## 2 Точка Старта

- Есть исходный `fintech-risk-service`: Python/Streamlit, batch data builder,
  daily stress-proxy baseline и три сохранённых модельных артефакта.
- Датасет заканчивается 07.06.2026. Существуют известные validation gaps:
  maturity у границ fold, unknown/warm-up target и различие fitted/OOS curves.
- Есть P1/P2-A, интервью и карта статистических источников. Это evidence для
  требований, не готовое разрешение переносить все исследовательские веса.
- Live worker, production database, серверное развёртывание и домен пока
  не подтверждены. В просмотренном коде нет готовой Docker/Compose конфигурации.
- Основной рынок RU и публичная регистрация выбраны. Первая аналитическая
  задача, horizons, числовой budget, домен, hosting, точные источники,
  права показа и эксплуатационные нормативы ещё не утверждены полностью.
- Research Git-перенос отменён. Личные интервью и переписка остаются локально;
  product dirty worktree пользователя сохраняется без откатов.

## 3 Рабочая Архитектура

Предлагаемый начальный вариант для умеренной нагрузки, не утверждённый стек:

```text
Браузер
  -> app.<выбранный-домен> / HTTPS
  -> reverse proxy и контроль доступа
       -> web UI
       -> Python API /api/v1

Разрешённые внешние источники
  -> отдельный ingest worker / scheduler
  -> immutable source snapshots
  -> normalised observations / quality / revisions
  -> PostgreSQL: history, signals, warnings, user state, audit
  -> feature snapshot и serving inference
  -> API / dashboard / reports

Отдельно: monitoring, logs, off-server backups, artifact registry
Обучение: отдельный controlled job, не действие пользователя в браузере
```

Рабочие кандидаты: Python API на FastAPI, PostgreSQL, Caddy для HTTPS/reverse
proxy и Docker Compose для управления сервисами на одном VPS. Существующий
Streamlit сохраняем, если он выдерживает согласованные UX/access/performance
сценарии; иначе меняем UI по отдельному решению. Не начинаем с переписывания
всего проекта или обязательных Kubernetes/Kafka/Redis.

Один сервер означает общую точку отказа. Такой вариант требует согласованного
уровня доступности и внешних backups; он не называется high availability.
При требованиях высокой доступности проектируем отдельную схему и бюджет.

Техническая опора: [FastAPI containers](https://fastapi.tiangolo.com/deployment/docker/),
[Compose production](https://docs.docker.com/compose/how-tos/production/).
Документация подтверждает механизмы, не достаточность конкретного VPS или
готовность нашего приложения. Версии зависимостей фиксируются после проверки.

## 4 Этапы Работы

### Этап 0 Спецификация V1

Утвердить первый сценарий: кто пользуется, что контролирует, какое действие
следует за сигналом. Зафиксировать географию, список показателей, задачи,
горизонты, роли, alerts, reports, API, языки и поддерживаемые устройства.
Определить ожидаемую одновременную нагрузку, update latency, допустимую
задержку и время восстановления. Все числа согласовать, не переносить FAR
или horizon из исследования без обоснования продуктовой задачей.

Результат: [release specification](v1_product_specification/README.md),
40 сценариев приёмки, список обязательного и отложенного, реестр решений
и backlog. **Документы подготовлены; G01/G02 ещё pending.**

### Этап 1 Перенос Знаний И Решения По Данным

Для каждой функции связать требование с исследованием, интервью или
статистикой; отделить эмпирический вывод, качественную гипотезу и аналогию.
Составить конечный каталог series/instrument IDs с units, calendar, time zone,
периодом истории, доступностью и source rights.

Выбрать поставщиков и тарифы для live/delayed/day/macro data. Проверить право
на display, non-display/model use и передачу клиентам, а также доступность
API из предполагаемого региона hosting. До платной подписки проверить её
условия и покрытие, не покупать один только доступ без нужных прав.

Результат: разрешённый data contract и определённый live coverage. JST остаётся
research-only; P2-B/P3/P4 и модели команды не получают автоматической приёмки.

### Этап 2 Воспроизводимая Кодовая Основа

Сохранить текущие snapshots/metrics/weights; создать новую версию product
outputs. Организовать configuration, migrations, unit/integration tests,
dependency lock, единый запуск и contracts для observations/features/signals.
Убрать абсолютные локальные пути из нового рабочего кода, не переписывая
исторические research manifests. Учёт часовых поясов и версий обязателен.

Результат: другой разработчик запускает разрешённую локальную систему
по инструкции без ручной правки данных и без автоматического обучения.

### Этап 3 Постоянный Контур Данных

Реализовать provider adapters, scheduler, incremental updates и отдельный
backfill. Сохранять source time/publication time, received time, revisions,
snapshots и quality flags. Добавить rate limits, bounded retries, timeout,
idempotency, atomic publication и защиту от двух одновременно активных jobs.

Рыночный feed, обновление UI и частота модельного inference независимы.
Рабочий ориентир UI 15-60 секунд пока не SLA; real-time или delayed режим
зависит от провайдера. Daily/macro ряды обновляются по их собственному календарю.
См. [детальный live-план](arcshift_v1_live_data_plan.md).

Результат: реальные новые разрешённые observations поступают автоматически,
а дубликаты, пропуски, пересмотры, 429 и отключения обработаны и протестированы.

### Этап 4 Модель И Валидация

Сначала исправить maturity, unknown targets и календарную семантику; добавить
regression tests. Затем по конечному согласованному run plan сравнить baseline
и необходимые candidates на той же задаче и выборке. Calibration и пороги
выбираются внутри development data, не на outer test.

Проверить AUC/AP, calibration/Brier, warning burden, false alarms, пропуски,
lead time, последние периоды и зависимость от эпизодов. Зафиксировать criteria
до outer results. Сохранить все неудачи, а не только удачную модель.

Результат: принят конкретный serving candidate или оформлено ограничение
функции. Для daily модели подаются валидные daily features, не случайный
неполный intraday bar. Новый weights artifact не заменяет старый молча.

### Этап 5 Сервис И Состояние Пользователя

Реализовать read API, history queries, signal provenance, watchlists, alerts,
review states/notes, report generation и audit trail. Разделить shared market
data и принадлежащие пользователю/организации notes/settings/exports.
Inference использует approved model version; запрос не вызывает fit или
прямой запрос к внешнему provider. Кэш связан с snapshot/version, а не вечен.

Результат: versioned API и сквозные integration tests, в том числе ошибки,
пустая история, unsupported task, stale state и нарушение доступа.

### Этап 6 Полноценный Интерфейс

Собрать рабочее место: обзор, наблюдение, история, детализация показателя,
карточка предупреждения, факторы, качество данных, review/notes, отчёты,
настройки и методология. Главный экран сразу рабочий, без обязательного
marketing landing. Проверить desktop/mobile, фильтры, loading/error/empty
states и отсутствие визуальных перекрытий.

Время последних данных отличается от времени refresh. Нет данных не означает
низкий риск. Fitted historical curves отделены от OOS и live. Drivers не
выдаются за причинность, а статус модели виден в контексте сигнала.

Результат: пользователь проходит основной процесс без ручного вмешательства
разработчика и получает согласованный snapshot в UI и export.

### Этап 7 Доступ И Эксплуатация

Публичный сервис с регистрацией требует authentication/session handling,
подтверждения почты, восстановления доступа и server-side authorization.
Проверить secure cookies, CSRF/CORS, rate limits регистрации/писем/API, истечение
сессии, изоляцию пользовательских данных, защиту exports и admin paths.
Staging закрыт от посторонних. Не отключать защиту ради работы reverse proxy.

Добавить structured logs без tokens/PII, health/readiness checks, job heartbeat,
alerts об outage/stale/failed backup, retention, backup encryption и runbooks.
Хранилище секретов не входит в образ, исходники, чат или browser bundle.
[Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/) можно
использовать для ограниченного доступа сервисов; защищать host-файлы всё равно
нужно, это не самостоятельная зашифрованная secret vault.

Результат: тесты доступа и отказов пройдены, назначен ответственный за реакцию,
есть проверенный способ отката и восстановления.

### Этап 8 Тестовый Сервер

После выбора hosting развернуть закрытый staging: отдельные настройки, БД,
users, secrets и storage от production. На одном VPS изоляция через отдельные
Compose projects допустима только при достаточных ресурсах и ясной границе
доступа; отдельный staging VPS предпочтителен при доступном бюджете.
Тестовые fixtures не смешиваются с production observations.

На сервер передаётся минимальный release artifact: code/image, migrations,
допущенные model artifacts и нужные configurations. Не копируется весь
ArcShift, raw интервью, переписка, books, .venv или JST research archive.
Доставка образа может быть ручной через защищённый канал; upload research
в GitHub для этого не требуется. CI/CD настраивается отдельно при согласовании.

Проверить реальный HTTPS/WebSocket путь, длительные UI sessions, фоновые
обновления, provider reachability, restart/reboot, logging и backups.
Staging не создаёт неучтённый второй poller: отдельный provider budget/fixtures.

Результат: release candidate работает на сервере и проходит сквозной прогон.

### Этап 9 Сквозная Приёмка

Проверить данные -> features -> signal -> UI -> alert -> review -> report/API.
Сопоставить snapshots, timestamps, значения и права. Выполнить негативные
тесты: provider disconnect, 429, broken schema, duplicate job, unavailable
features, истёкшая сессия, чужой workspace, плохой model artifact и failed job.

Провести нагрузочный тест на согласованной concurrency и объёме истории.
Проверить ограниченный живой прогон без реальных автоматических кредитных
или инвестиционных действий. Интерфейсное одобрение не является доказательством
экономического эффекта. Незакрытые release-blocking defects блокируют выпуск.

Результат: приёмочный отчёт по точной версии и разрешённый production release.

### Этап 10 Домен И Production Запуск

Домен можно зарегистрировать заранее после выбора имени; production DNS
переключается только после приёмки. Аккаунты registrar/hosting принадлежат
пользователю или команде, с 2FA, recovery и auto-renew под контролем владельца.

После отдельного разрешения на развёртывание:

1. Создать production environment и проверить доступность разрешённых источников.
2. Настроить SSH keys, ограниченный admin access, firewall и своевременные updates.
3. Открыть наружу HTTP/HTTPS; DB, model files и служебные API не публиковать.
4. Настроить DNS A; AAAA только при реально работающем IPv6. Имена
   `app.<домен>` и `staging.<домен>` здесь шаблоны, не существующие адреса.
5. Установить reverse proxy и HTTPS. Для Caddy нужны корректные DNS,
   доступный challenge path/порты и persistent certificate storage;
   [automatic HTTPS](https://caddyserver.com/docs/automatic-https) автоматизирует
   получение/renewal, но не заменяет проверку DNS и сертификата.
6. Загрузить проверенный immutable image и approved model/data versions,
   выполнить совместимые migrations и включить один production scheduler.
7. Проверить login, UI, API, WebSocket, свежесть, alerts, report и backup.
8. Выполнить контролируемый DNS/cutover, smoke tests и наблюдение после выпуска.
9. При нарушении согласованных критериев откатить release/model/config по runbook,
   учитывая совместимость DB schema; не откатывать БД вслепую с потерей новых notes.

Результат: рабочий ArcShift V1 на собственном HTTPS-домене с обновлением
данных, доступом, мониторингом, поддержкой и проверенным rollback.

### Этап 11 Сопровождение

Регулярно проверять source freshness, jobs, API errors/latency, disk/storage,
backups, доступы и уведомления; отдельно контролировать model drift/calibration
по мере созревания outcomes. Пересматривать thresholds/model только новой
версией и не выбирать их по прошлому outer test повторно.
Updates ОС/dependencies, renewal домена/тарифов, retention и restore drills
имеют владельца и расписание. Расходы и provider request budget наблюдаемы.

## 5 Сервер И Хранение

Первый sizing-кандидат для теста: Linux VPS порядка 4 vCPU, 8 GB RAM,
80-160 GB SSD. Это инженерный ориентир, не доказанная достаточность или
рекомендация покупать конкретный тариф. Размер выбирается после измерения
ingest volume, retention, model RSS, числа sessions и history queries.

Web/API/worker/DB работают в отдельных процессах/контейнерах с persistent
volumes и health checks. Тяжёлое обучение по умолчанию вне serving-сервера.
Контейнер не является backup, а restart policy не является high availability.

Ежедневный encrypted off-server backup — начальное предложение, не достаточный
RPO для любой задачи. Конкретные RPO/RTO и retention определяются в Этапе 0;
при необходимости добавляется более частый backup/WAL archiving. Восстанавливаем
БД, model artifacts, необходимые snapshots, конфигурацию и доступ к secrets.
Как минимум один restore выполняется в чистое окружение до production запуска.
[PostgreSQL backup documentation](https://www.postgresql.org/docs/current/backup.html)
описывает разные механизмы; выбранный механизм должен пройти наш restore test.

## 6 Зависимости И Параллельность

Критический путь: scope -> допустимые источники/таргет -> versioned inputs ->
валидированный candidate -> интегрированное приложение -> staging ->
приёмка -> production. Домен/hosting исследуем заранее, не покупаем вслепую.

После contracts работа идёт параллельно: data/live pipeline, model validation,
API/storage, UI/workflow. Infrastructure/monitoring создаются до окончания UI,
чтобы не выяснять deployment проблемы в последний день.

Предлагаемое распределение, не подтверждённые новые назначения: Ярослав с
агентом — scope/архитектура/API/интеграция; Настя — данные и providers; Никита —
рабочий процесс/UI; Мила — validation/tests/acceptance. Вклад, skills и время
команды нужно подтвердить. Security и production приёмку не оставлять только
автору соответствующего кода; ответственный за поддержку обязателен.

## 7 Сроки И Бюджет

Плановый ориентир обсуждения — 6-10 недель при регулярной работе четырёх
человек, конечном coverage и доступных правах/источниках. Это оценка, не
обещанный дедлайн; после Этапа 0 назначаем владельцев и календарь. Внешние
лицензии, recruitment и дополнительная model research могут увеличить срок.

Пользователь ограничил стартовую рамку сервером, доменом и хранением данных,
без числового лимита. Платный market feed не согласован. Сначала проверяем
разрешённые варианты в этой рамке, не предполагая бесплатное право display.
Учитываем отдельно домен/год, VPS/месяц, storage, off-server backup и
транзакционную почту аккаунтов. Последние две потребности нельзя убрать
только потому, что они не названы отдельным тарифом. Market feeds/entitlements
и дополнительные каналы требуют нового решения. Не фиксируем цены или
поставщика без актуальной проверки и бюджета.

Для выполнения потребуются: approved scope, budget ceilings, домен, выбранный
hosting/регион, допущенные источники в рамках бюджета и способ предоставления доступов.
Пароли и API keys не надо отправлять в чат; secrets настраиваются защищённо.
План не требует покупать сервер прямо сейчас.

## 8 Условие Выпуска

Release возможен только при прохождении [release checklist](arcshift_v1_release_checklist.csv)
для одной версии кода/данных/модели. DNS и красивая страница сами по себе
не означают готовность V1. Основной следующий результат — спецификация
Этапа 0 с подтверждёнными workflow, coverage, критериями и ответственными.

Новые deployment scripts, инфраструктура, numeric acquisition, training,
DNS изменения, платные подписки, Git upload и внешняя передача материалов
этим планом не выполнены и автоматически не разрешаются.
