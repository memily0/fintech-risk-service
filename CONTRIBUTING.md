# Разработка ArcShift 2.0

## Базовый процесс

`main` — единая интеграционная ветка с проверенным кодом. Рабочие ветки создаются от актуального `main`, а изменения возвращаются через Pull Request. Направления обозначаются префиксами:

- `feature/data/<краткая-тема>` — источники, таргеты и подготовка признаков;
- `feature/models/<краткая-тема>` — обучение, модели и прогнозирование;
- `feature/research/<краткая-тема>` — P1/P2 и эксперименты;
- `feature/product/<краткая-тема>` — интерфейс, светофор и сервис;
- `fix/<краткая-тема>` и `chore/<краткая-тема>` — исправления и инфраструктура.

Эти ветки описывают область изменения, а не отдельные варианты проекта. После merge весь принятый код находится в `main`. Постоянные ветки направлений пока создавать не нужно.

## Pull Request

1. Синхронизируйте рабочую ветку с актуальным `main` до открытия PR.
2. Ограничьте PR одной понятной задачей; не смешивайте перенос данных, рефакторинг продукта и изменение модели.
3. Опишите цель, затронутые каталоги, способ проверки, влияние на данные/модели и известные ограничения.
4. Убедитесь, что CI прошёл. Проверки, требующие закрытых данных, секретов или сети, не должны быть обязательными без подготовленной инфраструктуры.
5. Получите ревью владельца затронутой области. Изменения методологии, таргета или риск-интерпретации требуют ревью Lead Risk Analyst.
6. Не добавляйте секреты, неподтверждённые наборы данных и тяжёлые артефакты обычным Git.
7. Выполняйте merge только после устранения замечаний и подтверждения воспроизводимости.

Рекомендуемые настройки GitHub для `main`: обязательный PR, успешный CI, минимум одно одобрение, сброс одобрений при новых изменениях и запрет force push. Они настраиваются владельцем репозитория в GitHub и не задаются файлами этого изменения.

## Стиль и тесты

- Предпочитайте небольшие функции, ясные имена и прямой поток данных.
- Не вводите класс или слой абстракции без конкретной потребности.
- Добавляйте тест для расчёта или преобразования, ошибка в котором влияет на риск-оценку.
- Не делайте сетевые запросы и не используйте крупные данные в обычных unit-тестах.
- Обновляйте документацию при изменении команды запуска, схемы данных или структуры каталогов.

Перед PR выполните:

```bash
python -m compileall -q app scripts tests
python -m unittest discover -s tests -p "test_*.py"
```

## Данные и модели

Каждый новый набор данных должен иметь источник, дату получения, лицензию/условия использования, схему и воспроизводимый способ построения. Файлы в `data/raw/`, `data/processed/`, `data/external/` и `models/artifacts/` по умолчанию игнорируются.

Если объём или частота обновления потребуют версионирования бинарных файлов, команда отдельно выбирает Git LFS или DVC:

- Git LFS — для небольшого числа версионируемых файлов, которые должны следовать за Git-ревизией;
- DVC — для воспроизводимых пайплайнов и наборов данных во внешнем объектном хранилище.

До принятия такого решения не коммитьте новые большие CSV, модели или результаты экспериментов.
