# Постановка Задачи ArcShift V1

Дата: 06.11.2026. Контракт: `v1-task.1`.
**Бизнес-постановка согласована. Измерение цели и модель ещё не приняты.**

**Дополнение 08.11.2026.** Документ ниже фиксирует исходное решение о задаче.
[Новая методика измерения](v1_stress_measurement.md) закрывает выбор формулы
для проверки и заменяет пятикомпонентную гипотезу в действующем контракте
`v1-task.2`. Реальные источники и эмпирическая валидность не подтверждены.

## 1. Краткое Определение

ArcShift помогает риск-аналитику следить за российской рыночной средой
и проверять предупреждения о **новом эпизоде рыночного стресса
в следующие 30 календарных дней**. Глобальные показатели используются
как внешний контекст России, а не как обещание прогноза для других стран.

Пользователь подтвердил предмет задачи и основной горизонт 06.11.2026.
Это выбор продуктовой задачи для проверки, а не доказательство того,
что 30 дней оптимальны, что модель полезна или что индекс корректно измеряет стресс.

## 2. Пользователь И Решение

| Вопрос | Зафиксированная граница |
| --- | --- |
| Для кого | Риск-аналитик, наблюдающий внешнюю рыночную среду России |
| Для чего | Приоритизировать проверку изменений и подготовить собственный вывод |
| Что делает аналитик | Проверяет данные, источники и факторы, фиксирует разбор и отчёт |
| Чего сервис не решает | Купить/продать актив, выдать кредит, изменить капитал или ставку |
| Где доступен прогноз | Только Россия; прочие страны не являются обещанным покрытием |
| Какой эффект уже доказан | Улучшение решений, снижение потерь и экономический эффект пока не доказаны |

Наблюдение за данными, прогноз события и решение человека являются тремя
разными объектами. Закрытие разбора человеком не становится меткой отсутствия
стресса и не служит доказательством правильности прогноза.

## 3. Текущий Стресс И Будущее Начало

Пусть `E(t)` означает известное наличие порогового стресса на дату `t`.
Конкретное измерение `E` ещё предстоит зафиксировать.

Основная прогнозная задача применяется **только при известном `E(t)=0`**:

```text
Y30(t) = 1, если в датах t+1, ..., t+30 появляется пороговый стресс;
Y30(t) = 0, если весь этот интервал известен и стресса в нём нет;
Y30(t) = unknown, если исходы ещё не созрели или окно неполно.
```

При известном отсутствии стресса сегодня первое будущее стрессовое состояние
является началом нового порогового эпизода. Отдельная минимальная длительность
или период восстановления здесь не предполагаются; их введение изменит цель
и потребует новой версии до эксперимента.

| Состояние на дату прогноза | Как трактовать |
| --- | --- |
| `E(t)=0` | Дата входит в выборку риска нового начала (`at_risk`) |
| `E(t)=1` | Стресс уже идёт: текущий мониторинг; прогноз нового начала не применяется |
| `E(t)=unknown` | Текущее состояние неизвестно; прогноз нового начала недоступен |
| Нет допущенной модели/входов | Прогноз недоступен, даже если задача согласована |

Уже идущий стресс исключается из выборки нового начала, **не кодируется нулём**.
Прогноз продолжения/длительности текущего эпизода был бы другой задачей.

## 4. Время И Доступность

- Основной горизонт: **30 календарных дней**, окно `(t, t+30]`.
- День `t` не является будущим; `t+30` включён; `t+31` не включён.
- Единица наблюдения: одна дневная дата прогноза России, не отдельная компания.
- Данные признаков должны быть реально известны к cutoff прогноза,
  а не просто иметь более раннюю дату наблюдения.
- Частота обновления котировок не меняет горизонт и не делает прогноз intraday.
- Точное время дневного cutoff, часовые пояса источников, торговые/неторговые
  дни, публикационные задержки и допустимый carry-forward определяются
  в следующем контракте источников; сейчас они не выдуманы.
- Синтетический helper требует все календарные дни. Это защитная проверка,
  не разрешение заполнять выходные будущими или недоступными значениями.
- Метка известна только при полном окне и `label_end <= outcomes_available_through`.
  В обучении дополнительно требуется строгое `label_end < fold_cutoff`.

Горизонты 7 и 90 дней сохранены в истории как кандидаты. Они **не утверждены**
для текущего прогнозного сервиса и не выбираются по лучшим уже увиденным метрикам.

## 5. Что Считать Стрессом

Есть исходная гипотеза: среднее пяти стандартизованных компонент
(VIX, волатильность USD/RUB, волатильность и просадка IMOEX, инверсия ОФЗ).
Это **не принятый индекс**, не CISS и не официальная кризисная хронология.
Отсутствующую обязательную компоненту нельзя молча убрать из среднего.

До обучения на реальных данных нужно отдельно зафиксировать:

1. Точные ряды, единицы, знаки, формулы волатильности/просадки/спреда.
2. Календарь и доступность каждой компоненты, причинный warm-up и стандартизацию.
3. Состав, веса и порог события, основание их выбора без подгонки по test.
4. Соответствие индекса российскому стрессу, а не только внешнему VIX;
   зависимые компоненты IMOEX не выдаются за независимые подтверждения.
5. Правила эпизодов, проверочные исторические случаи и независимые индикаторы.
6. Версию цели, данных и допустимые пересмотры исторических меток.

Порог `1.0` и rolling-окна из legacy-кода не становятся научно обоснованными
от этого документа. Передача `threshold=1.0` в синтетическом тесте проверяет
программную семантику, а не экономический смысл порога.

## 6. Выход И Доказательство Качества

После допуска выход должен связывать задачу/горизонт, дату прогноза,
information cutoff, snapshot данных, версии модели/цели/policy и ограничения.
Число нельзя называть вероятностью без проверки калибровки.

Пока модель не допущена, API возвращает `signal=null`, а не нулевой риск.
Состояние `already_in_stress` в offline-разметке не является рассчитанным
текущим состоянием рынка в работающем интерфейсе.

Дальнейшая проверка должна отдельно оценивать ранжирование, калибровку,
пропуски **эпизодов**, ложные предупреждения и время до начала. Соседние
дневные прогнозы не считаются независимыми кризисами. Сравнение с простой
базой проводится на одинаковых датах и зрелых метках, с временным holdout.
Допустимая нагрузка предупреждений, цена ошибок и критерии допуска требуют
предварительного выбора до просмотра итоговых результатов; чисел здесь нет.

## 7. Реализация И Граница Завершения

- Канонический машиночитаемый паспорт: `arcshift_v1/task_definition.py`;
  read-only `GET /api/v1/models/task`, без зависимости от рыночного snapshot.
- Новый task ID: `ru_market_stress_onset_v1`.
- Кандидат измерения: `composite_stress_onset_candidate.1`, `pending_freeze`.
- Model-readiness API: `v1-model-readiness.2`; 30 дней утверждены для задачи,
  не для допуска модели. Запросы 7/90 дней и старого task ID дают `unsupported`.
- `models/validation/onset.py` проверяет новую семантику на synthetic данных.
  Исходные temporal helper и legacy future-presence target сохранены отдельно.
- Старые веса, оценки и банковские benchmark-результаты не переносятся
  на новый target как подтверждённое качество.

Блок «Постановка задачи» закрыт на уровне бизнес-вопроса и временной семантики.
Это **не** закрывает полный функциональный scope V1, data admission, измерение
цели, model validation, operating policy, public launch или коммерческие права.
Если прогноз не проходит проверку, переход к monitoring-only требует отдельного
пересмотра обещанного продукта, а не объявления всей V1 готовой.

## Методологические Ориентиры

Разделение текущего индикатора и будущего предупреждения принципиально:
[Holló, Kremer, Lo Duca (2012), CISS](https://www.ecb.europa.eu/pub/pdf/scpwps/ecbwp1426.pdf)
измеряет текущий стресс, с иной агрегацией и набором индикаторов. Этот источник
не валидирует нашу пятикомпонентную гипотезу.

[Drehmann, Juselius (2013), BIS WP 421](https://www.bis.org/publ/work421.pdf)
рассматривает требования к банковским early-warning индикаторам с учётом решений
и времени реакции. Он не обосновывает 30-дневный горизонт нашей иной задачи.
