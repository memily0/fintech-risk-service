# ArcShift V1: задания на релизный спринт

Старт: 13.11.2026, МСК. Интеграционная ветка: `v1/integration-yaroslav`.
Минимальная база по коду: `732371b` (локальное восстановление доступа).
Для нового PR взять опубликованный коммит, в котором находится этот пакет:
интегратор подтверждает полный SHA после приёмки. Целевой срок первого общего
кандидата: 48–72 часа от старта. Закрытый staging и публичный V1 — разные выпуски.

## Что делаем и чего не обещаем

- Пользовательский путь: обзор России и история → предупреждение → личный
  разбор → сохранённый отчёт PDF/CSV/JSON. Список наблюдения и аккаунт сохраняются
  при перезапуске. Сравниваем с MVP по функциям, а не переносим прежние веса и UI.
- Задача модели: новый эпизод российского рыночного стресса в следующие 30
  календарных дней. Не прогноз системного банковского кризиса и не 7/90 дней.
  Первая модель: заново обучаемая L2-логистическая регрессия. Сначала один
  заранее описанный прогон, без перебора моделей и параметров по итоговому тесту.
- На закрытом staging используем придуманные данные и аккаунты `.test`.
  `signal=null` означает «прогноз недоступен», а не вероятность 0%. Тестовые
  числа не выдаём за результат боевого расчёта. Сейчас `/api/v1/signals/current`
  отдаёт `signal=null`; контур обновления и боевой расчёт ещё не подключены.
- Не ждём ответа Мосбиржи, чтобы писать и тестировать код. Для реального ряда
  отдельно фиксируем основание для получения, хранения и внутреннего расчёта,
  отдельно — для публичного показа ряда или производного результата. Фоновый
  запуск, платный пилот и публичный показ не взаимозаменяемы. Не заполняем
  обязательный ряд похожим индикатором без новой спецификации и проверки.
- За рамками этого спринта: платёжный кабинет, автопереобучение, дополнительные
  горизонты, расширение перечня факторов, миграция старого продукта целиком.

## Как открыть PR

1. Выполнить `git fetch origin`. Сохранить свой текущий diff. Открыть новую
   ветку `v1/rc-data-nastya`, `v1/rc-model-mila` или `v1/rc-ui-nikita` от
   зафиксированного интегратором SHA. Старые ветки не переписывать. Переносить
   только нужный код или патчи, не вливать старую ветку целиком.
2. В первый контроль, не позже T+24 ч, принести небольшие независимые PR, даже
   если live-часть заблокирована. Целевая ветка PR — `v1/integration-yaroslav`,
   не `main`. Изменение общего контракта или миграции согласовать до реализации;
   не дублировать маршруты и не использовать уже занятые номера `006/007`.
3. В описании указать: базовый SHA, задачу, изменённые файлы/контракты, способ
   проверки, фактический вывод тестов, отрицательные сценарии, что не сделано,
   блокер и следующего владельца. Для миграции указать тест обновления с
   предыдущей версии и способ восстановления. Для UI приложить скриншоты.
4. Коммитить только свой diff. Не публиковать токены, письма, рабочие базы,
   логи с персональными данными, закрытые исследования или недопущенную историю
   и веса. В журнале называть источник и основание доступа без закрытых деталей.
5. В общий статус: `готово / в работе / блокер`, ссылка на PR, следующий шаг.
   «Прошло на синтетике» и «прошло на реальных данных» писать отдельно.

## Настя: данные и расписание

**Вход:** `src/arcshift_data`, текущий `arcshift_v1/market.py`,
[интеграция истории](v1_data_integration.md) и [методика](v1_stress_measurement.md).
Не создавать второй HTTP API истории или независимое хранилище снимков.

1. Заполнить матрицу по трём обязательным рядам: IMOEX, USD/RUB, ОФЗ 10Y.
   Для каждого указать точный идентификатор, единицу, источник и поле, календарь,
   дату и время наблюдения/публикации/получения, тип ревизий, лимиты, основание
   использования и что ещё неизвестно. Если ищем другого поставщика, проверяем
   именно тот же ряд и применимость его условий. Наличие HTTP 200 не является
   допуском. До подтверждения доступ для реального ряда выключен по умолчанию.
2. Сделать один запускаемый вручную job для той же логики, которую вызовет
   расписание: загрузить → проверить → записать ревизии → атомарно опубликовать
   валидный снимок. Синтетический адаптер/мок позволяет проверить без сети.
   Повтор на том же входе не создаёт новый снимок; частичный сбой или гонка
   не перезаписывает активный снимок. Не смешивать реальные и тестовые данные.
3. Согласовать с Милой и Никитой контракт до патча: `snapshot_id`, версия
   источника и дата наблюдения, фактическое `available_at`/время получения,
   отсечка, покрытие и причина `stale`/`missing`/`market_closed`/`unknown`.
   Это перечень смыслов, не разрешение добавлять одноимённые поля в действующий
   API без ревью. Просроченная или неизвестная доступность не равна спокойствию.
4. Покрыть тестами: запланированное закрытие vs пропуск в открытый день,
   неизвестный календарь, поздняя запись после 09:00 МСК, дубликат, ревизия,
   таймаут, неверная схема и повтор запуска. На неуспехе последнее корректное
   значение сохраняется с его исходной датой, а причина видна отдельно.

**Результат PR:** команда запуска, матрица по рядам, тесты на придуманных
данных, зафиксированный сценарий отказа. Реальную пробу запускаем только по
ряду, для которого отдельно подтверждены нужные действия; пишем фактическую
дату проверки и что было доступно к отсечке. Недель наблюдений заранее не ждём.

## Мила: модель и единственный исторический прогон

**Вход:** `models/validation`, [контракт цели](v1_task_definition.md),
[описание кандидата](v1_forecast_candidate.md) и текущие `/api/v1/models/status`,
`/api/v1/signals/current`. Не менять целевое событие, основной горизонт и
состояние публичного сигнала ради демонстрации.

1. До любого реального fit оформить версионируемый протокол: версии цели и
   признаков, календарные границы разбиений, когда метка считается зрелой,
   какие пропуски делают дату недоступной, какие можно обработать на train,
   минимальное число эпизодов/дней и покрытие, правило выбора порога,
   критерии принятия и что делать с неопределённостью. Интегратор ревьюит
   протокол до просмотра итогового теста. Не считать неизвестные даты нулями.
2. Подготовить воспроизводимый CLI/модуль обучения и расчёта. Для теста —
   синтетические входы, фиксированный seed и версия схемы артефакта. Артефакт
   связывает версию модели, хеш методики/входа, список признаков, порог и дату
   обучения. Деплой не загружает пользовательский путь или непроверенный
   бинарный объект. Фоновый результат привязывается к дате и `snapshot_id`;
   без достаточных входов или версии артефакта результат отсутствует.
3. Защитить отсечку на **каждой** исторической дате: поздняя ревизия даже
   внутри train fold не меняет признаки более раннего прогноза; окно метки
   должно быть зрелым до границы обучения. Модель и оба эталона сравниваются
   на одних датах. Порог подбирается на development, не на итоговом holdout.
4. После допуска истории и протокола выполнить один прогон. Для вероятности
   сравнить с частотой события в train (Brier и пригодность калибровки);
   для предупреждений — с правилом повышенного текущего стресса. Указать
   знаменатели, пропущенные/непроверяемые эпизоды, тревоги не менее чем за
   5 календарных дней, долю ложных тревожных дней (рабочий предел 10%),
   покрытие, устойчивость по периодам и итог `допуск / отказ / мало данных`.

**Результат PR:** синтетические тесты временной доступности, пропуска и
несовместимого артефакта; шаблон отчёта исторического прогона и команды.
До допуска — модель можно подготовить и тестировать, но API для клиентов
по-прежнему возвращает `signal=null`. Старые коэффициенты MVP не подставляем.

## Никита: дашборд и путь до отчёта

**Вход:** `arcshift_v1/static`, `tools/smoke_v1_workbench.cjs`,
[очередь и список наблюдения](v1_warning_workspace.md). Из существующего
follow-up `67ee914` переносить обзор и графики, не альтернативную миграцию
`006`, backend очереди или новый формат личного разбора.

1. Использовать `GET /api/v1/market/series`, историю ряда, статус модели и
   текущий сигнал. Сохранить общие `/workspace/warnings`, `/workspace/reviews`,
   `/workspace/series-watchlist` и `/workspace/reports` под `/api/v1`.
   Если для обзора нужен серверный запрос последнего окна, сначала согласовать
   его с Настей: первая страница отсортированной по возрастанию истории не
   гарантирует актуальную последнюю точку. Добавить сценарий на 501 запись.
2. Различать свежие, устаревшие, недоступные и синтетические данные.
   «Рынок закрыт» показывать только по серверному календарю, не по локальным
   часам. Пропуск не превращать в ноль на графике. При `signal=null` не брать
   число из демонстрационного сценария и не рисовать 0%.
3. Сохранить цепочку: открыть предупреждение → начать/продолжить разбор →
   сохранить → открыть отчёт и скачать PDF/CSV/JSON. Исходный снимок отчёта
   не должен меняться при обновлении данных. Проверить, что обновление снимка
   и перезапуск не создают дубликаты предупреждений и не теряют разбор.
4. Проверить desktop 1440 px и mobile 390/320 px, длинные названия и пустые
   состояния. Тест двумя аккаунтами: владелец скачивает отчёт, другой с
   действующей сессией не получает карточку и файлы. Вложения PR — только
   синтетические скриншоты; исключить коды восстановления и токены.

**Результат PR:** браузерный тест и скриншоты трёх ширин. В первом PR —
обзор/график/состояния на общем API, без миграций; спорные расширения отдельно.

## Ярослав: интеграция и решение о выпуске

- **T+0–24 ч:** зафиксировать базу, опубликовать проверенный SHA, раздать этот
  пакет; проверить хост/доступ, выбрать закрытый staging и подготовить
  отдельную БД. Данные, модель и интерфейс разрабатываются одновременно.
- **T+24–48 ч:** принять PR по контрактам, не сливать целые старые ветки.
  Объединить обновление, модельный статус и обзор. На отдельной БД выполнить
  чистую установку, миграции, проверку двух пользователей и восстановление.
  Для живого кандидата нужен отдельный отчёт допуска источников и модели.
- **T+48–72 ч:** собрать один проверенный SHA и зафиксировать go/no-go.
  Публичный `v1.0.0` только при готовых данных, модели, эксплуатации и
  подтверждении владельца; иначе публикуем проверенный код/RC, оставляем
  прогноз выключенным и записываем открытые условия. Не выдаём RC за V1.
- Настоящая почта и аккаунты — отдельная задача, не снятие `.test`-ограничения.
  Нужны окружение и домен, проверенный отправитель, доставка и resend, защита
  токенов и сессий, лимиты, постоянная БД, миграции и оператор. Секреты идут
  через секрет-хранилище хоста, не в PR, почту или чат. Перед открытием сайта
  проверяем HTTPS, две реальные тестовые учётки, логи, алерты, backup и restore.

Команды, границы тестового запуска, восстановление и релизная ведомость:
[инструкция по staging](v1_staging_runbook.md).
