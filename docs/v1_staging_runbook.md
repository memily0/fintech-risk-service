# ArcShift V1: закрытый staging и приёмка

Этот порядок запускает **синтетическую сборку для команды**. Приложение
принимает только `local`/`test`, `synthetic` и loopback; настоящая почта,
автоматическое получение реальных котировок и допущенный прогноз отсутствуют.
Не публикуйте этот процесс через домен, открытый порт, публичный туннель или
reverse proxy. Доступ к удалённому staging — только через согласованный SSH
доступ. На macOS воспроизводим локально; Linux и удалённый хост требуют
отдельной проверки. [Задания команде](v1_release_handoff.md).

## Проверка выбранного коммита

Из Git checkout нужны Git, Bash и Python 3.14. Для браузера нужны Node,
Playwright (предыдущий прогон: 1.62.1) и установленный браузер. `NODE_PATH`
должен быть абсолютным, так как проверка работает во временном каталоге.

```sh
bash tools/check_v1_candidate.sh <SHA>
NODE_PATH=/path/to/node_modules ARCSHIFT_RUN_BROWSER=1 \
  ARCSHIFT_PLAYWRIGHT_CHANNEL=chrome bash tools/check_v1_candidate.sh <SHA>
```

Проверка извлекает Git-архив, ставит зафиксированные зависимости в новые
окружения, гоняет приложение и офлайн-валидацию. Опционально гоняет браузер.
Затем собирает wheel, ставит его в третье окружение и запускает оба HTTP-smoke
вне исходников. Все БД временные. Для офлайн-запуска можно передать
`PIP_NO_INDEX=1 PIP_FIND_LINKS=/absolute/path/to/wheelhouse`, где содержатся
все зависимости для выбранной версии Python, ОС и архитектуры. Если браузер
пропущен, это не считается его приёмкой. Успех не означает допуск прогноза.

## Установка пакета и запуск

1. На согласованном хосте нужен непривилегированный пользователь, Python 3.14,
   возможность держать процесс под менеджером сервисов и отдельный постоянный
   каталог. Для Linux сначала повторить проверку коммита там; результаты
   macOS не заменяют её. SSH-доступ выдаётся только нужным операторам.
2. Собрать wheel из чистого архива выбранного SHA по командам из
   [проверки дистрибутива](v1_local_acceptance.md#повторный-прогон). Передавать
   на хост сам wheel и `requirements-v1.lock`, не рабочий checkout с датасетом.
   Записать полный SHA и SHA-256 файла wheel, сверить перед установкой.
3. В чистом каталоге с wheel и lock-файлом под пользователем сервиса:

```sh
umask 077
python3.14 -m venv .venv
.venv/bin/python -m pip install -r requirements-v1.lock ./arcshift_local_integration-*.whl
.venv/bin/python -m pip check
mkdir -p "$HOME/.local/state/arcshift-staging"
export ARCSHIFT_ENVIRONMENT=test ARCSHIFT_DATA_MODE=synthetic
export ARCSHIFT_HOST=127.0.0.1 ARCSHIFT_PORT=8765 ARCSHIFT_STORAGE_BACKEND=sqlite
export ARCSHIFT_DB_PATH="$HOME/.local/state/arcshift-staging/fixtures.sqlite3"
.venv/bin/python -m arcshift_v1
```

Для постоянного staging оператор переносит **те же** настройки в менеджер
сервиса, указывает абсолютные пути к Python и БД и проверяет перезапуск. Не
использовать локальную рабочую или будущую production БД. Порт приложения
не открывать в firewall. Для доступа разработчика к удалённому хосту:

```sh
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:8765:127.0.0.1:8765 <operator>@<staging-host>
```

В браузере открыть `http://127.0.0.1:8765/`; если этот порт занят локально,
изменить только левый порт проброса. Не использовать `ssh -g`. Токен
подтверждения `.test`-аккаунта оператор получает **на хосте** через
`python -m arcshift_v1.dev_outbox --email analyst@example.test` в том же
окружении и с тем же `ARCSHIFT_DB_PATH`. Токены не прикладывать к логам и PR.

## Приёмка и отказные сценарии

1. На хосте и через туннель: `/livez`, `/readyz`, `/`,
   `/api/v1/auth/capabilities`, `/api/v1/models/status`,
   `/api/v1/signals/current`. Проверить, что готовность положительная,
   `production_ready=false`, `real_mail_delivery=false`, `signal=null`.
   Отдельно проверить, что прямой сетевой доступ к порту приложения отсутствует.
2. Зарегистрировать два `.test`-аккаунта, подтвердить локальными кодами.
   Первый открывает предупреждение, создаёт разбор, сохраняет отчёт,
   скачивает PDF/CSV/JSON. Второй не видит чужую карточку и файлы.
   Проверить сброс пароля, недействительность старого пароля и старой сессии.
3. Проверить, что перезапуск оставляет аккаунт, разбор и отчёт, а его сохранённый
   снимок не меняется. Когда jobs и модель интегрированы, добавить прогон
   `job → snapshot_id → расчёт → UI → отчёт` на синтетике и повтор с таймаутом.
   Ожидаем: не опубликованы ошибочный снимок, свежий прогноз и дубли. До этого
   такой сквозной прогон отмечаем как **не выполненный**, даже при зелёном UI.
4. Снять копию SQLite командой `.backup` через `sqlite3`, не копировать один
   файл активной базы в режиме WAL. Проверить `PRAGMA integrity_check` на копии.
   Восстановление репетировать на отдельном пути и порту: с копии открыть
   отчёт и сравнить его содержимое. Не подменять активную БД ради проверки.
5. Для обновления сохранить предыдущий wheel, его lock и предмиграционную
   копию. При откате остановить процесс; если схема изменилась, запустить
   предыдущий wheel на восстановленной **предмиграционной** БД. Зафиксировать
   возможную потерю записей после точки backup. Не ставить старый код поверх
   новой схемы без доказанной совместимости.

## Ведомость выпуска

| Что фиксируем | Что считается результатом |
| --- | --- |
| Сборка | SHA, дата и МСК, ОС, Python, хеш wheel, результаты тестов |
| Staging | Владелец, доступ для команды, путь/тип БД без секретов, проверка loopback, резервная копия и восстановление |
| Источники | Разрешённые действия и ряды, версия снимка, часы публикации и ожидаемая свежесть, владелец сбоя |
| Модель | Версии цели и артефакта, подтверждённый протокол, историческая оценка и решение о показе |
| Production | HTTPS, БД и почта, изоляция, мониторинг, проверенный откат, оператор, решение владельца о выпуске |

Если внешний хост не согласован, указываем «локальная репетиция» и её
результаты, не «staging развёрнут». Если данные/модель не допущены, указываем
«прогноз выключен» и конкретный блокер. Не выдаём synthetic RC за `v1.0.0`.
